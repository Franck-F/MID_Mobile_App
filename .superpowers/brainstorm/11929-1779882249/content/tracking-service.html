Section 4 / 7 — Service de tracking temps réel

Node + Socket.io · Redis adapter · interpolation checkpoints + GPS opt-in

Flux des données pendant la course
SOURCE A · Puces RFID checkpoints
  1. Coureur traverse un checkpoint (5km, 10km, 15km, 21km, 30km, 42km)
  2. Prestataire chrono envoie événement via webhook signé → POST /tracking/checkpoint
  3. Tracking service écrit en Redis (clé runner:{id}:checkpoints) + déclenche broadcast
  4. Fallback : polling toutes les 30s si le webhook tombe
✅ 100% des coureurs · obligatoire (résultats officiels)
SOURCE B · GPS smartphone (opt-in)
  1. Coureur active le mode "Tracker live" dans l'app
  2. App envoie position GPS toutes les 10s via WebSocket
  3. Tracking service stocke en Redis (TTL 24h) + broadcast
  4. Perte réseau → bufferisation locale SQLite → flush au retour
~10-20% des coureurs estimés · expérience premium
⇣
📡 TRACKING SERVICE (Node + Socket.io)
Ingestion
Reçoit webhooks chrono + WS GPS · valide · idempotent
Interpolation
Entre 2 checkpoints, estime position sur polyline parcours · allure constante
Broadcast
Diffuse aux spectateurs abonnés via Socket.io rooms (1 room par coureur)
⇣
👀 Spectateur
S'abonne à 1-5 coureurs favoris → rejoint leurs rooms WS → reçoit positions en push (toutes les 5s pour les coureurs sans GPS, en temps réel pour ceux avec GPS)
💬 Cheer me
Spectateur envoie message court → NestJS persiste + rate limit (max 10/coureur/spectateur) → Tracking service pousse au coureur via WS + notif push fallback

Scalabilité race-day

Cible : 5000 coureurs + ~15000 spectateurs = ~20k connexions WS simultanées pendant 5h
Stack : 3 instances tracking service derrière nginx, Socket.io Redis adapter pour broadcast cross-instance, sticky sessions au load balancer
Pré-scale : 48h avant la course, on monte de 1 à 3 instances · downscale +24h après
Capacité par instance : ~10k connexions Socket.io confortables sur un VPS OVH B2-15 (4 vCPU / 15 Go RAM, ~50€/mois)
